## 2. 핵심 메시지 (한 문장)

> **통제의 목적은 Agent의 자율성을 없애는 것이 아니라, 자율성의 경계를 설계하는 것이다.**

부제: 게이트가 있어야 맡길 수 있다.

## 3. 전개 원칙 — 이 세션이 지키는 네 가지 규칙

1. **Harness를 먼저 정의하지 않는다.** 문제를 하나씩 해결하고, 마지막에 "우리가 만든 해결 구조 전체가 Harness였다"로 도달한다.
2. **문제는 선언하지 않고 목격시킨다.** 문제 목록은 표로 먼저 던지는 것이 아니라, 도입부의 실행 로그 리플레이 한 장면에서 도출한다.
3. **모든 요소는 문제의 답으로만 등장한다.** Hook · Record · Policy · State · Limits · Validation · Approval — 어떤 요소도 문제 없이 소개되지 않는다.
4. **스코프 밖은 숨기지 않고 선언한다.** 다루지 않는 것(재시도 *전략*)은 마무리에서 명시하고 2차 예고로 흡수한다.

## 4. 전체 전개 구조

```text
통제되지 않은 Agent (목격)
        ↓
문제 7가지 도출
        ↓
Hook        "실행 과정에 개입한다"
        ↓
Record      "무슨 일이 있었는지 남긴다"
        ↓
Policy      "무엇을 허용할지 정한다"        (allow / deny)
        ↓
State       "현재 상황을 관리한다"
        ↓
Limits      "실행의 경계를 정한다"
        ↓
Validation  "실제 성공 여부를 확인한다"     → 실패 시 재시도 → Limits 재등장
        ↓
Approval    "필요한 판단은 사람에게 맡긴다"  (Policy가 allow/deny/ask 로 확장)
        ↓
Harness     "Agent가 일하는 실행 환경을 설계한다"
```

## 5. 장별 구성

### 0장. 도입 — 그냥 맡겨본다 (10분)

- 가장 단순한 그림에서 시작: `User → Agent → Tools (File / Shell / Git / Test)`
- 첫인상: "알아서 잘하는데?"
- **실행 로그 리플레이** (구성된 예시임을 명시): 통제 없는 Agent의 실행 기록을 스크롤로 재생한다.
  - 프로젝트 밖 파일을 수정한다
  - `rm` / `sudo` 를 실행하려 한다
  - 같은 명령을 수십 번 반복한다
  - "작업 완료했습니다" — 실제로는 테스트 실패
  - 그리고 이 모든 과정이 **아무 데도 기록되어 있지 않다**
- 리플레이를 되감으며 선언: **"방금 우리는 7가지 문제를 목격했습니다."**
- 문제 테이블 도출 (= 세션 로드맵, 이후 장마다 한 줄씩 지워나간다):

| # | 문제 | 핵심 질문 | 답 (요소) |
|---|---|---|---|
| 1 | 실행 과정에 개입할 수 없다 | 중요한 순간에 끼어들 수 있는가? | Hook |
| 2 | 무엇을 했는지 남지 않는다 | 나중에 실행 과정을 확인할 수 있는가? | Record / Trace |
| 3 | 해서는 안 되는 행동도 한다 | 무엇을 허용하고 금지할 것인가? | Policy |
| 4 | 현재 실행 상황을 알 수 없다 | 지금 어떤 상태인가? | State |
| 5 | 너무 많이 실행하거나 범위를 벗어난다 | 어디까지 허용할 것인가? | Limits |
| 6 | Agent의 "완료"를 믿을 수 없다 | 정말 완료된 것인가? | Validation |
| 7 | 중요한 판단까지 Agent가 해버린다 | 어디에서 사람이 결정해야 하는가? | Approval |

> 슬라이드에서는 "답" 열을 도입 시점에 비워두고, 각 장이 끝날 때마다 채운다.

### 1장. 개입할 수 없다 → Hook (12분)

- 질문: Agent가 Tool을 실행하려는데, 실행 전후에 끼어들 수 없다면 어떻게 통제할까?
- 구조: `Agent → Before Hook → Tool → After Hook → Agent`
- 정의: **Agent의 실행 과정 중 특정 지점에 외부 로직을 삽입할 수 있게 하는 메커니즘**
- Before Hook의 용도: 검사 · 기록 · 차단 · 입력 변경 / After Hook의 용도: 결과 기록 · 오류 검사 · 후처리
- 핵심 구분: **Hook은 통제 정책 자체가 아니라, 통제를 넣을 수 있는 지점이다.**
- **데모 1 — 관찰 Hook**: opencode plugin `tool.execute.before` 로 모든 도구 호출을 로그로만 남긴다.
- **데모 2 — 개입 Hook**: 같은 자리에서 조건 검사 후 `throw` 한 줄로 도구 실행을 차단한다.
  - 메시지: 관찰과 개입은 같은 지점에서 코드 몇 줄 차이다.

### 2장. 남지 않는다 → Record / Trace (8분)

- Hook을 얻고 가장 먼저 하는 일은 통제가 아니라 **기록**이다.
- 타임라인 예시:
  ```text
  10:31 READ  src/main.cpp
  10:32 EDIT  src/main.cpp
  10:33 RUN   pytest
  10:34 FAIL  test_login
  ```
- "기록도 진화한다"는 **한 장으로 압축**: 단순 로그 → 구조화 → 실행 추적/감사 기록. (하위 용어 사다리를 펼치지 않는다 — 용어 부하 방지)
- 메시지: **통제하려면 먼저 무슨 일이 일어났는지 남길 수 있어야 한다.**

### 3장. 해서는 안 되는 행동을 한다 → Policy (8분)

- 기록을 보니 문제 행동이 보인다: 프로젝트 밖 파일 수정, `rm`, `sudo`, 허용되지 않은 Tool, 외부 접근.
- Policy 예시: `src/ 이하만 수정 가능 / sudo 금지 / rm 금지 / network 금지 / 허용된 Tool만`
- 이 시점의 Policy는 **allow / deny 이분법**으로 소개한다. (→ 7장에서 ask 로 확장된다)
- 관계 정리: **Hook = 어디에서 검사할 것인가 / Policy = 무엇을 검사할 것인가**

### 4장. 현재 상황을 알 수 없다 → State (7분)

- 기록만으로는 매번 처음부터 재구성해야 한다.
- State 예시: `current_phase / modified_files / tool_call_count / validation_status / approval_status`
- 핵심 구분: **Trace = 지금까지 무슨 일이 있었는가 / State = 그 결과 지금 어떤 상태인가**

### 5장. 너무 많이 실행한다 → Limits (7분)

- State가 있으니 실행량을 통제할 수 있다.
- 예시: Tool 호출 최대 20회 / 최대 10분 / 수정 파일 최대 10개 / Token·비용 상한
- 구조: `State → Limits → Allow / Block`
- 메시지: **자율성을 주되, 무한한 자율성을 주지는 않는다.**
- 이쯤부터 Hook 모음이 아니라 "실행 환경"처럼 보이기 시작한다.

### 6장. "완료"를 믿을 수 없다 → Validation, 그리고 재시도 (10분)

- Agent: "작업 완료했습니다." → 실제: Build Fail / Test Fail / 출력 파일 없음 / 요구사항 누락
- 원칙: **Agent의 주장과 실제 성공은 다르다.**
- 구조: `Agent Output → Validation (Build / Test / Lint / Schema / Requirement) → Success / Failure`
- **실패 이후 — 화살표 하나를 추가한다**: 실패 결과를 Agent에게 돌려주고 다시 시킨다 (재시도).
- 그러면 질문이 생긴다: **"몇 번까지 다시 시키나?" → 아까 만든 Limits가 여기서 다시 등장한다.**
  - `Validation 실패 → 재시도 → Limits(재시도 상한) 초과 → 중단`
  - 이 순간이 세션 전체 메시지의 첫 실증이다: **요소들은 연결되어 함께 작동한다.**
- 스코프 경계 (슬라이드에 명시): 재시도의 *존재와 상한*까지만 다룬다. 재시도 **전략**(무엇을 어떻게 다르게 다시 시킬 것인가)은 2차 실습에서.

### 7장. 판단까지 맡길 수 없다 → Approval (8분)

- 정책상 허용된 행동이라도 사람이 최종 판단해야 하는 일이 있다: 대량 삭제, 배포, PR Merge, 운영 변경, 외부 시스템 Write.
- 등장 논리: **Policy의 판정값이 allow / deny 이분법에서 allow / deny / ask 삼분법으로 확장되는 순간, Approval이 태어난다.**
  - "되긴 되는데, 물어봐야 하는 일" = `ask`
- 구조: `Agent → Policy 판정(ask) → Approval Required → Human → Allow / Reject`
- 핵심 메시지 재등장: **통제의 목적은 자율성을 없애는 것이 아니라, 자율성의 경계를 설계하는 것이다.**

### 8장. 다시 처음 그림을 본다 → Harness (7분)

- 처음 그림(`User → Agent → Tool`)을 다시 띄우고, 지금까지 만든 요소를 얹는다.
- 최종 다이어그램은 **층으로 그린다** (요소를 상자 안에 흩어놓지 않는다):

```text
┌─────────────────────────── Harness ───────────────────────────┐
│                                                               │
│  통제 평면        Policy      State      Limits               │
│                     │           │          │                  │
│  실행 경로   User → Agent → [Hook] → Tool → [Hook] ─┐         │
│                          │                          │         │
│  기록                    └────── Record / Trace ────┘         │
│                                                               │
│  출구 게이트              Validation ──실패──▶ 재시도(상한)   │
│                              │성공                            │
│                           Approval (ask) → Human              │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

- 그리고 **이 시점에 처음으로 Harness를 정의한다**:
  > 우리는 Harness를 만들기 위해 시작한 것이 아니다.
  > Agent를 실제 업무에 사용하면서 발생하는 문제를 하나씩 해결했고,
  > 그 해결책들이 연결되어 하나의 실행·통제 환경이 되었다.
  > **그것이 Harness다.**

### 9장. 마무리 (5분 + Q&A 15분)

- 문제 테이블 재등장 — 7칸이 모두 채워져 있다.
- 오늘 다루지 않은 것 (명시): 재시도 **전략**, 그리고 이 모든 것을 직접 만드는 일.

## 8. 2차 세션과의 연결

- 1차 마지막에 **Harness 설계 템플릿**을 배포한다 (2차 실습에서 레벨마다 한 칸씩 채운다):
  1. 어떤 이벤트에 끼어드는가 (Hook)
  2. 무엇을 기록하는가 (Record)
  3. 무엇을 허용/금지/질문하는가 (Policy: allow / deny / ask)
  4. 무엇을 추적하는가 (State)
  5. 한도는 얼마인가 (Limits)
  6. 완료를 무엇으로 판정하는가 (Validation)
  7. 누가 승인하는가 (Approval)
- 2차 세션 흐름(확정된 골격): 통제되지 않은 Agent 실행 → Hook 추가 → 범위 통제 → 도구 통제 → 실행 제한 → 완료 검증 → 사람 승인 → Harness 완성

## 9. 결정 기록 (Decision Log)

| 결정 | 근거 |
|---|---|
| 문제 주도형 전개 (Harness를 마지막에 정의) | 청중이 용어를 외우는 게 아니라 필요를 따라가게 하기 위함 |
| 문제 목록은 도입 리플레이에서 "목격"으로 도출 | 추상 목록 선(先)제시의 인지 부하 회피 |
| 팀/도메인 특화 비유 배제, 쉬운 일반 예시 사용 | 번역 계층 없이 바로 이해되는 예시가 더 효과적 |
| Approval은 Policy의 ask 확장으로 도입 | 별도 메커니즘의 갑작스러운 등장 방지, 실제 도구의 permission 모델과 일치 |
| 재시도는 "존재+상한(Limits 재소환)"까지만, 전략은 2차로 | 분량 관리 + Validation과 Limits의 연결 순간 확보 |
| 기록의 하위 용어 사다리는 한 장으로 압축 | 신규 용어 7개 상황에서 용어 부하 방지 |
