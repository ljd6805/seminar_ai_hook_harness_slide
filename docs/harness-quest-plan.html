Harness Quest
실행의 경계를 직접 만든다.

같은 요청도 통제 구조에 따라 다른 결과를 냅니다. 기록하고, 허용 범위를 정하고, 실행을 제한하고, 결과를 검증하는 과정을 하나의 실습으로 연결합니다.

기획안부터 작성 · 사용자 선택120분 기본안 · 제안Lv.0–6 공동 실습 · 제안실습 코드·채점기는 제작 전

1차 이론 세션은 사용자 설명에 따라 완료로 취급합니다. 이 문서는 2차 실습을 위한 제안이며, 새 운영 방식과 시간 배분은 아직 확정되지 않았습니다.

02 / SCENARIO

미션은 “주문 집계 보고서를 작성하고 제출하라”입니다.

제품 지식이 필요 없는 작은 업무를 사용합니다. Agent는 주문 자료를 읽어 집계 결과를 만들고 제출하려 합니다. 참가자는 이 과정에 필요한 통제 규칙을 단계적으로 추가합니다.

Agent에게 주는 요청

“입력 주문의 금액을 합산해 output/summary.json과 output/report.md를 작성하세요. 검증을 통과하면 제출을 요청하세요.”

샘플 입력: 10,000원 + 5,000원 − 할인 2,000원.
정상 합계: 13,000원. 정수 원 단위를 사용합니다.

실습의 완료 조건

  • 입력 자료와 보호 파일이 바뀌지 않습니다.
  • 결과 파일의 스키마와 합계가 맞습니다.
  • 검증을 통과한 바로 그 결과에 대해 사람이 승인합니다.
  • 승인 후 모의 제출이 한 번만 일어납니다.
가상 프로젝트 경로역할기대하는 접근
input/orders.json주문 원본읽기만 허용합니다.
output/summary.json항목 수·통화·합계를 가진 결과작성 후 스키마와 값을 검증합니다.
output/report.md집계 설명을 담는 업무 산출물 예시파일 존재와 필수 항목을 검사합니다. 설명 품질은 사람이 검토합니다.
protected/settings.json변경하면 안 되는 기준 파일쓰기 요청을 거부하고 원본 보존을 확인합니다.
../other-project/config.json범위를 벗어난 요청 예시쓰기 전에 차단합니다.

위 경로는 앞으로 제작할 실습의 제안입니다. 현재 저장소에 이 파일들이 준비되어 있다는 의미는 아닙니다. report.md는 교육용 업무 산출물이며, 프로젝트 기획·개발 문서는 HTML로 작성합니다.

기본 실습의 실행 범위: 도구 어댑터는 메모리 안의 가상 파일과 모의 제출 기록만 다룹니다. 삭제·프로젝트 밖 쓰기·임의 Shell 요청도 실제 운영체제 명령으로 실행하지 않습니다. 이것은 교육용 모델이며, 실제 파일시스템의 심볼릭 링크나 프로세스 격리를 검증한 보안 샌드박스가 아닙니다.
03 / LEARNING FORMAT

규칙의 효과를 먼저 확인하고, 실제 Agent에 연결합니다.

기본 실습 · 제안

고정 요청으로 통제 로직 검증

강사가 제공한 시나리오가 도구 호출 요청을 같은 순서로 재생합니다. 참가자가 작성한 규칙에 따라 허용·차단·대기 결과가 달라집니다.

확인할 수 있는 것: 통제 함수의 결과, 실행 횟수, 상태 전이, 산출물 검증, 승인 범위.

이 시나리오는 모델의 추론이나 실제 OpenCode 실행 기록이 아닙니다. 화면에도 “고정 시나리오 재생”을 표시합니다.

연결 확인 · 조건부

같은 규칙을 OpenCode에 연결

동일한 정책 함수를 호출하는 얇은 어댑터를 사용합니다. 등록된 실습 도구 한정으로 Hook이 호출되고 차단·기록이 작동하는지 확인합니다.

추가로 확인할 것: 실제 도구 이름, 입력 형식, 이벤트 전달, 오류 처리와 권한 동작.

사전 호환성 확인을 통과하면 수료 정리 시간에 강사가 시연합니다. 실패하면 고정 시나리오 실습까지만 완료로 기록합니다.

역할하는 일하지 않는 일
참가자규칙을 설계하고 TODO 함수를 완성하며 판정 이유를 설명합니다.기반 실행기와 모든 도구를 처음부터 만들지는 않습니다.
작성 보조 Agent코드 작성·오류 해석·추가 테스트 아이디어를 돕습니다.“통과했다”는 자기보고로 채점을 대신하지 않습니다.
시나리오 제공자정상·실패·경계 조건의 고정 요청과 후보 산출물을 제공합니다.LLM의 판단을 재현했다고 주장하지 않습니다.
채점기와 강사실제 호출 흔적·상태·결과를 검사하고 마지막 설명을 확인합니다.새 요구사항을 숨겨서 참가자를 탈락시키지 않습니다.
STEP 1문제 재현

어떤 요청이 왜 잘못 통과했는지 봅니다.

STEP 2규칙 수정

한 번에 한 가지 통제 함수를 추가합니다.

STEP 3다시 채점

정상·금지·경계 요청을 함께 확인합니다.

STEP 4이유 설명

예상과 실제 결과를 비교한 뒤 다음 단계로 갑니다.

이전 Skill Quest의 “미션 → 채점 → 다음 레벨” 구조는 이어갑니다. 캐릭터·성장 코드·별도 웹 보드는 기본 실습의 검증이 끝난 뒤 추가할 선택 기능으로 둡니다.

준비된 “통제가 빠진 경로”와 “정상 경로”를 각각 재생합니다. 집계 파일이 만들어졌어도 보호 파일 변경, 무한 반복, 틀린 합계 또는 무승인 제출이 남아 있음을 확인합니다.

참가자가 할 일
문제가 발생한 이벤트를 고르고, Hook·Policy·Limits·Validation·Approval 중 필요한 통제를 연결합니다.
통과 기준
최소 네 가지 실패를 실행 전 통제와 실행 후 검증으로 나누어 설명합니다. 이 단계에는 프로그래밍 점수를 부여하지 않습니다.
제공 자료
가상 파일의 실행 전후 차이, 시나리오별 요청 목록, 빈 설계 템플릿. 관찰용 강사 기록은 참가자가 구현할 Trace와 구분합니다.
Lv.1 · 실행 전후에 흔적을 남깁니다 15분 · Hook + Record

같은 도구가 여러 번 호출돼도 각 요청의 시작과 결과를 연결할 수 있도록 기록합니다.

참가자가 작성할 부분
onBefore(request), onAfter(request, result)와 record(event)의 빈칸을 채웁니다. 실행기는 강사가 제공합니다.
통과 기준
허용된 호출 하나마다 같은 runId·callId를 가진 시작·종료 기록이 있습니다. 성공과 오류를 구분하고, 오류에도 종료 기록이 누락되지 않습니다.
검사 예시
같은 파일을 두 번 읽어도 호출 ID가 섞이지 않습니다. 이후 레벨에서는 차단·승인 대기도 결과 유형으로 기록합니다.
학습 질문
기록에 “실행 시도”만 있으면 실제로 실행됐는지 어떻게 구분할까요?
Lv.2 · 허용한 파일 범위만 바꿉니다 15분 · 경로 정책

output/에는 결과를 쓰되, 원본과 보호 파일을 바꾸는 요청은 도구 실행 전에 거부합니다.

참가자가 작성할 부분
checkPath(action, path)를 완성합니다. 강사가 제공한 경로 정규화 함수로 논리 경로를 정규화한 뒤 디렉터리 경계를 비교합니다.
통과 기준
output/summary.json 쓰기는 허용합니다. input/orders.json, output-other/x.json, output/../../protected/settings.json 쓰기는 거부하고 가상 도구를 호출하지 않습니다.
채점 범위
기본 실습의 경로 표기는 슬래시를 사용하는 가상 경로입니다. 실제 OS 경로·심볼릭 링크 검사는 연결 단계의 별도 항목으로 둡니다.
학습 질문
startsWith("output")만 사용하면 어떤 요청이 잘못 통과할까요?
Lv.3 · 도구 이름과 입력을 함께 검사합니다 15분 · 도구 정책

파일 경로가 허용돼도 모든 종류의 행동이 허용되는 것은 아닙니다. 등록한 도구와 정해진 입력 형태만 통과시킵니다.

참가자가 작성할 부분
decideTool(request)에서 허용 목록과 입력 검사를 연결합니다. 이 단계에서는 read_file, write_file, run_check만 허용합니다.
통과 기준
알 수 없는 도구, 임의 Shell 요청, 필수 인자가 없는 요청을 거부합니다. run_check는 등록된 검사 ID만 받습니다.
검사 예시
단순한 문자열 블랙리스트 대신 도구 의미와 인자를 검사합니다. 정상 보고서 본문에 “rm”이라는 글자가 있어도 이유 없이 쓰기를 차단하지 않습니다.
학습 질문
“금지 단어가 없다”와 “허용한 행동이다”는 같은 뜻일까요?
Lv.4 · 현재 상태를 이용해 실행을 멈춥니다 15분 · State + Limits

차단된 요청을 계속 반복해도 전체 실행이 끝나도록, 시도 횟수와 실제 실행 횟수를 따로 셉니다.

참가자가 작성할 부분
reserveBudget(state)와 상태 갱신을 완성합니다. 기본안은 요청 시도 최대 8회이며, 실행 전 시도 횟수를 예약합니다.
통과 기준
8번째 요청까지 판정할 수 있고, 9번째 요청은 도구 실행 없이 한도 초과로 종료됩니다. 정책에 거부된 시도도 8회에 포함합니다. 새 실행은 카운터가 0에서 시작합니다.
제공 자료와 범위
State에는 attempted, executed, phase, validation, approval을 둡니다. 기본 실행기는 순차 실행만 지원하며, 병렬 예약·시간·비용 한도는 확장 과제로 남깁니다.
학습 질문
실행에 성공한 호출만 세면, 금지 요청을 반복하는 Agent를 멈출 수 있을까요?
Lv.5 · 산출물을 확인하고 필요한 경우만 재시도합니다 15분 · Validation + 재시도 분류

Agent의 완료 메시지와 무관하게 결과 파일을 읽어 스키마, 정수 합계, 입력 보존 여부를 검사합니다. 실패 이유는 다음 시도의 입력으로 전달합니다.

참가자가 작성할 부분
validateArtifact(files)와 classifyFailure(result)를 완성합니다. JSON 파서, 합계 비교용 입력, 고정된 다음 후보를 반환하는 시나리오 제공자는 준비해 둡니다.
통과 기준
틀린 합계·필수 필드 누락·원본 변경을 성공으로 처리하지 않습니다. 수정 가능한 결과 오류는 최초 시도 후 최대 2회만 재시도합니다. 전체 요청 상한도 계속 적용합니다.
재시도 전략의 최소 범위
산출물 오류는 구체적인 실패 내용을 전달해 다시 생성합니다. 일시적인 모의 도구 오류는 같은 요청을 제한적으로 재시도합니다. 정책 위반·승인 거절·한도 초과는 자동 재시도하지 않습니다.
예제의 한계
“실패 후 수정된 후보”는 고정 시나리오로 제공됩니다. 실제 모델이 실패를 해석해 수정했는지는 OpenCode 연결 실험에서 따로 확인합니다.
Lv.6 · 검증한 결과에 대해서만 승인을 받습니다 15분 · Approval + 통합

publish_release 요청을 추가하고 allow / deny / ask를 연결합니다. 제출은 외부 서비스 호출 대신 모의 제출 목록에 한 항목을 추가합니다.

참가자가 작성할 부분
requestApproval(candidate)과 canPublish(request, approval)를 완성합니다. 사람이 보는 화면에는 대상 파일, 변경 요약과 검증 결과를 보여줍니다.
통과 기준
검증 전 제출은 거부합니다. 검증 후에는 승인 대기 상태가 되며, 승인 전과 거절 후에는 제출 횟수가 0입니다. 동일한 산출물 버전에 대한 승인 후에만 1회 제출합니다.
필수 경계 검사
승인 후 결과가 바뀌면 승인과 검증 상태를 무효화합니다. 다른 실행의 승인, 대상이 다른 승인, 사용한 승인의 재사용을 거부합니다. 해시 계산은 제공 함수로 처리합니다.
마지막 확인
처음의 실패 시나리오를 다시 실행하고, 정상 집계와 제출은 성공하면서 금지된 동작은 실행되지 않는지 확인합니다.
Lv.7 자율 과제 제안: 자신의 업무를 한 가지 골라 설계 템플릿의 7칸을 채웁니다. 실제 시스템에 연결하기 전에 모의 입력으로 정상·금지·실패 사례를 각각 한 개 이상 작성합니다. 수료 필수 범위에는 넣지 않습니다.
05 / TARGET STRUCTURE

승인은 필요한 행동을 실행하기 전에 받습니다.

요청을 받아 실행 여부를 결정합니다.

Agent 요청→Before Hook · 기록→State · Limits · Policy

기본 실습은 고정 시나리오가 요청을 공급합니다. 연결 확인에서는 OpenCode가 요청을 공급합니다.

allow · 실행

도구를 실행하고 결과를 기록한 뒤 State를 갱신합니다. 파일을 변경하면 이전 검증·승인이 여전히 유효한지 확인합니다.

deny · 중단 또는 거부

도구는 실행하지 않습니다. 거부 이유와 실행 여부를 기록하고, 회복 불가능한 위반은 현재 실행을 종료합니다.

ask · 대기

대상·인자·산출물 버전을 묶어 승인을 요청합니다. 승인된 요청도 실행 직전에 버전과 정책을 다시 검사합니다.

Validation · 결과 확인

산출물을 검사하고 실패를 분류합니다. 재시도는 기존의 전체 예산 안에서 이루어집니다. 제출은 검증 통과와 유효한 승인을 모두 요구합니다.

Hook은 개입 지점이고, 정책·상태·검증은 그 지점에서 연결할 로직입니다. 이 실습은 실행 통제를 배우기 위한 작은 Harness이며, 컨텍스트 관리·모델 라우팅·분산 실행까지 구현하는 과정은 아닙니다.

승인 요청의 최소 정보

{
  runId, requestId, tool, normalizedArgs,
  artifactHash, validationResult,
  decision, consumed
}

위 구조는 설계 예시이며 현재 API 사양이 아닙니다. 보류·거절·승인 후 변경·중복 제출을 구분할 수 있는지를 기준으로 구현합니다.

06 / ACCEPTANCE

“모두 차단”도 통과할 수 없게 채점합니다.

각 레벨은 정상 요청이 성공하는지와 금지 요청이 실행되지 않는지를 함께 확인합니다. 로그에 “차단”이라는 문구가 있는 것만으로 통과시키지 않고, 도구 호출 횟수와 가상 파일의 변화까지 검사합니다.

검사입력 또는 상황통과 조건
정상 경로읽기 → 13,000원 집계 작성 → 검사 → 승인 → 제출정확한 결과가 한 번 제출됩니다.
범위 위반입력 원본, 비슷한 접두사의 폴더, 상위 경로에 쓰기도구 실행 전 거부하고 보호 데이터가 그대로입니다.
도구 위반미등록 도구·잘못된 인자·임의 Shell 요청도구 호출 횟수가 증가하지 않고 이유가 기록됩니다.
횟수 경계시도 상한 8회에 대해 8번째와 9번째 요청허용 여부 판정과 전체 중단의 경계를 정확히 구분합니다.
거짓 완료완료 메시지는 있지만 합계가 15,000원Validation이 실패하고 제출되지 않습니다.
재시도 상한수정 가능한 오류가 계속 발생최초 시도 + 최대 2회 재시도 후 종료합니다. 전체 예산이 먼저 끝나면 그때 종료합니다.
승인 범위승인 후 수정·다른 실행의 승인·승인 재사용제출을 막고 새 검증 또는 새 승인이 필요함을 기록합니다.

반복 가능한 채점

매번 같은 초기 가상 파일과 시나리오로 실행합니다. 시간 대신 이벤트 순서와 호출 ID를 검사해 불필요한 흔들림을 줄입니다. 정답 기대값은 참가자 정책 함수로 계산하지 않습니다.

공정한 난이도

요구사항과 경계 조건은 공개합니다. 채점에서는 값과 경로를 바꾼 사례를 추가합니다. 정답 문자열을 하드코딩한 구현과 정상 요청까지 막는 구현은 통과하지 못하도록 합니다.

채점기·시나리오·정답 스냅샷은 참가자 수정 대상에서 제외합니다. 로컬 실습이므로 악의적인 채점기 변조를 완전히 방지하는 시험 시스템은 아닙니다. 강사가 기준 배포본으로 최종 확인하는 운영안입니다.

기록의 최소 형식

runId · callId · event · tool · decision · reason
attempted · executed · resultStatus · artifactHash

비밀값이 포함될 수 있는 모든 입력을 무조건 기록하는 방식은 피합니다. 수업은 가짜 데이터만 사용하고, 실제 적용 과제에서는 기록 대상·마스킹·보관 기간을 설계 템플릿에 덧붙입니다.

빠른 참가자의 확장

새 경계 사례를 추가하거나 시간 제한을 구현합니다. 다만 병렬 실행, 영속 상태 복구, 실제 OS 격리는 별도 과제로 분리합니다. 수업 중 공통 실습의 범위를 늘리지 않습니다.

학습 난이도 가정: 참가자는 조건문·객체·함수를 읽을 수 있고 OpenCode 기본 사용을 경험했습니다. 인원·운영체제·코딩 숙련도·사용 가능한 모델은 아직 확인되지 않았습니다. 120분은 리허설 전의 운영 제안입니다.

기획 → 작은 시제품 → 교재 → 리허설 순서로 만듭니다.

단계완료할 작업문서와 증거다음 단계 조건
A · 이번 기획미션·진행·통과 기준·미결 사항 정리이 문서, 문서 허브실습 방식·환경·시간을 선택합니다.

C · 실습 키트Lv.0–6, 시작 코드, 체크포인트, 채점기, 해결 예제 작성참가자 교재 HTML, 강사용 해설 HTML, 검증 보고서 HTML정상 해답 통과와 의도적으로 잘못 만든 구현의 실패를 확인합니다.
D · 발표·연결진행 슬라이드, OpenCode 어댑터, 환경 안내 작성슬라이드 HTML, 고정 버전·실제 실행 기록, 연결 확인표목표 환경에서 Hook·도구 이름·권한 처리와 예외 경로를 확인합니다.
E · 리허설깨끗한 환경에서 설치부터 수료까지 실행단계별 소요 시간, 실패 기록, 수정 사항선택한 수업 시간 안에 완료하고 초기화·복구 절차가 작동합니다.

위 구조는 제안이며 quest/ 코드는 아직 작성하지 않았습니다. 우선 기존 저장소에서 기획을 이어가고, 배포 단위가 달라질 때 별도 실습 저장소의 필요성을 판단합니다.

구현 기준: 함수는 100줄 이하로 작성합니다. 정책 판정과 부작용을 분리하고, 허용·차단·한도 경계·승인 무효화에 단위 테스트를 둡니다. 배포용 HTML은 외부 자산 없이 열 수 있게 만들고, 새로운 개발·검증 문서는 허브에 연결합니다.

실제 연결 전에 확인할 항목

  • 수업에 사용할 OpenCode 버전과 플러그인 API를 고정합니다. V1 예제를 V2에서 그대로 실행하지 않습니다.
  • 운영체제와 Node.js 버전을 고정하고, 회사 환경에서 설치할 수 있는지 확인합니다.
  • 실습 도구 외 경로를 통해 파일이나 네트워크에 접근하지 못하도록 대상 환경의 권한 설정을 검증합니다. 사용자 작성 Hook만으로 완전한 격리를 보장한다고 설명하지 않습니다.
  • 고정 시나리오 채점은 모델 없이 실행할 수 있게 합니다. 작성 보조 및 연결 실험의 모델·인증은 참가 조직에서 허용된 환경을 사용합니다.
  • 기본 실습의 모든 동작이 모의 실행인지, 실제 OpenCode 어댑터에서 검증한 동작인지 결과 화면에 구분합니다.
